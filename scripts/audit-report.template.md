## Netlify deployment: direct-URL 404 (root cause and fix)

**Symptom.** On 2026-10-07 `https://localpos.in/` loaded, but every other URL, for example `/solutions/retail-billing-software/`, answered with Netlify's "Page not found" (HTTP 404). So did `/sitemap.xml` and `/robots.txt`.

**Root cause (observed by requesting the live site on 2026-10-07).** Netlify was serving the output of a bare client build (`vite build`), not the output of this project's `npm run build`. The live home page still contained the literal template markers `<!--app-head-->` and `<!--app-html-->`, and its HTML matched, line for line, a local `vite build` output. There was no per-route HTML, no `404.html`, no `sitemap.xml` and no `robots.txt` on the live site. The repository had no `netlify.toml`, so Netlify used its own build settings. Either Netlify's auto-detected Vite command (`vite build`) or a manual upload of such a folder produced this; the Netlify dashboard was not inspected, so which of the two happened is **not confirmed**. Serving a local client-only build reproduced the symptom exactly: `/` 200, `/solutions/retail-billing-software/` 404, `/pricing/` 404, `/sitemap.xml` 404.

This is not a missing single-page-app fallback. The site is statically prerendered: `npm run build` writes one HTML file per route (`dist/<route>/index.html`) plus `404.html`, and the browser then hydrates that HTML. A catch-all `/* /index.html 200` rewrite would have hidden the missing pages by serving the empty template (no content for search engines) at every URL, and would have turned every genuinely unknown URL into a 200 response.

**Second problem found.** `VITE_SITE_URL` defaulted to `https://www.localpos.in`, while the live `www.localpos.in` answers with a 301 to `https://localpos.in/` (observed). A Netlify build with the defaults would have put `www` canonicals, Open Graph URLs and sitemap entries on every page, all pointing at a redirecting host.

**Fix.**

1. New `netlify.toml`: build command `npm run build && npm run verify`, publish `dist`, `NODE_VERSION=22`, `VITE_SITE_URL=https://localpos.in`. A `netlify.toml` build command overrides the Netlify dashboard setting. `npm run verify` fails the build (so the previous good deploy stays live) if a prerendered page is missing or broken.
2. No `_redirects` file and no `/* /index.html 200` rule, on purpose (see above): valid routes are real files, and any other URL gets `dist/404.html` with a true 404 status and `noindex`. Netlify serves a published `404.html` for unmatched URLs automatically.
3. New `tests/e2e/deploy.spec.ts` (regression guard) and an `E2E_SITE_ORIGIN` setting in `seo.spec.ts` so the tests can run against the Netlify-origin build.
4. README: Netlify deployment section.

The router already defined all 24 required routes and a catch-all `*` route that renders the custom 404 page; no application code changed. Trailing-slash URLs are the canonical form everywhere (links, canonicals, sitemap), matching the SEO document. No `/billing-software/` page exists.

## 12. Remaining warnings and limits (read before relying on this report)

1. **Forms send nothing yet.** No lead endpoint is configured (`VITE_LEAD_ENDPOINT`). The forms are tested end to end against an intercepted endpoint, and the shipped build shows a visible "Preview mode" notice. Until an endpoint is set, form submissions are not received by anyone.
2. **Placeholders remain by design:** pricing figures, contact details (email, phone, address, support hours) and the Login URL (`https://app.localpos.in/`) are marked placeholders because no real values were provided. Legal pages are templates and need review by the business and a lawyer before launch.
3. **SEO verifier warnings:** {{SEO_COUNTS}}. The warning is a keyword-frequency heuristic on the home page ("billing software" appears 14 times in the main content). The copy follows the keyword mapping supplied, so it was left as is; the owner may prefer to trim it.
4. **Browsers and devices:** automated tests ran only in Chrome with emulation. No test was run in Safari, Firefox or on a physical phone, and screen-reader behaviour was not tested manually, and focus trapping in the mobile drawer was not tested. Automated axe checks do not catch every accessibility problem.
5. **Visual review is partial:** screenshots were reviewed by eye for the pages and widths that the automated checks or earlier reviews pointed at, not for every page at every width, and 768 px was reviewed least. The automated checks cover all 33 routes at all 15 widths for overflow only, and that check cannot see content clipped by an `overflow: hidden` wrapper (see section 3).
6. **Lighthouse and timings** are from a local machine and a local server. Real-world Core Web Vitals on `localpos.in` have not been measured (the site has no traffic data).
7. **DNS and HTTPS:** DNS was not changed or tested by this work. On 2026-10-07 `localpos.in` answered from Netlify over HTTPS (with an HSTS header) and `www.localpos.in` redirected to it with a 301. The routing fix described at the top of this report is **not live until it is pushed and Netlify redeploys**, and nothing in this report verifies the live site after that.
8. **Security headers:** the Content Security Policy is delivered as a `<meta>` tag, and `netlify.toml` configures no response headers. Directives that only work as headers (such as `frame-ancestors`) therefore do not apply. No penetration testing was done. Google Analytics 4 and Microsoft Clarity were added after this audit's main test run; this report's speed and Lighthouse figures were measured without them.
9. **Mobile loading speed under throttling.** Lighthouse performance on mobile is 85 to 99 across the seven pages tested (home 85 once, 91 to 94 on repeats), and mobile LCP is above 2.5 s on four of them (see section 7). Desktop is 100 everywhere. Real-device and field performance have not been measured.
10. **Touch devices.** The desktop-menu fix (section 9) was reproduced and tested with a mouse. A tap on a touch screen wider than 1024 px was reasoned about, not tested.
